# Dense-block mining and coordinated-behaviour detection: algorithms, usability at GH Archive scale, use on software platforms, downstream use, and adversarial check of claim C2

*Research date: 2026-11-10. Claim under attack, C2: "Cross-event-type coordination structure, mined as dense blocks on an account x repository x event type x minute tensor, used as input features to a positive-unlabeled classifier, together with cluster-grouped data splits so that accounts from one coordinated network do not leak between train and test." ## Q1. What are the core algorithms and their current state of the art?

### Takeaway
The foundational dense-block family (CopyCatch 2013; FRAUDAR 2016; M-Zoom 2016 and M-Biz 2018; D-Cube 2017/2021; DenseStream and DenseAlert 2017) gives approximation guarantees of 1/2 (FRAUDAR) or 1/N (tensor methods) and is evaluated mostly on injected attacks and TCP dumps. Later work went two ways: tensor and streaming extensions up to 2022 (ISG+D-Spot, AugSplicing, CubeFlow, MonLAD), and from 2023 mainly fast or parallel densest-subgraph engines for graphs (Spade, Dupin) rather than new N-way tensor methods.

### Inferences
- Post-2022 progress is concentrated in graph densest-subgraph engineering rather than N-way tensors: the newest tensor-specific papers found are CubeFlow (2021), AugSplicing (2021) and MonLAD (2022).
- For an account x repo x event type x minute tensor, ISG's motivation is the key caution: blocks that are dense on only some modes (for example specific repositories and event types over irregular minutes) are the failure case for all-mode density methods such as M-Zoom and D-Cube. A minute-resolution event-type tensor may produce this pattern often.

- Numeric F-measure results for FRAUDAR, FlowScope, MonLAD and AugSplicing are mostly in figures and were not extracted. Treat those as "reported qualitatively here".

## Q2. Which implementations can run on a 4-mode tensor from about 272,000 to 6.5 million events on this hardware?

### Takeaway
M-Zoom/M-Biz (Java) and D-Cube's serial mode (Java) are the only maintained-enough N-way tools with an explicit "any number of dimensions" interface and published benchmarks far above this scale. FRAUDAR, SpecGreedy, spartan2 and StarScout's CopyCatch are bipartite-only. Compute is not the constraint; the bottleneck is modelling choices (time granularity, event-type mode).

### Cited Findings
- **M-Zoom/M-Biz**: `./run_mzoom.sh input_path output_path dimension density_measure num_of_blocks` with CSV tuples of dimension values and a final integer measure; density options ari, geo, susp, es_alpha; requires Java 1.7+. Callable from Python by subprocess — [user guide](https://raw.githubusercontent.com/kijungs/mzoom/master/user_guide.pdf). It ran on AirForce (7 modes, 648K tuples) and EnWiki (3 modes, 483M tuples) — [M-Zoom PDF](https://www.cs.cmu.edu/~kijungs/papers/mzoomPKDD2016.pdf). M-Zoom took 27.7 s on AirForce in D-Cube's Table 4 — [D-Cube PDF](https://www.cs.cmu.edu/~kijungs/papers/dcubeWSDM2017.pdf).
- **D-Cube serial**: `./run_single.sh input_path output_path dimension density_measure policy mass_threshold num_of_blocks`; dimension values must be integers 0..cardinality-1; the guide lists Hadoop 1.x.x and Java 1.6+ as prerequisites even for the package — [user guide](https://raw.githubusercontent.com/kijungs/dcube/master/user_guide.pdf). Memory O(Σ|R_n|); 15.6 s on AirForce; serial version handled 10^10 tuples — [D-Cube PDF](https://www.cs.cmu.edu/~kijungs/papers/dcubeWSDM2017.pdf).
- **DenseStream/DenseAlert**: Java API only (`public DenseStream(int order)`), any order; GPL-3.0; up to 85 GB used on its largest datasets — [user guide](https://raw.githubusercontent.com/kijungs/densealert/master/user_guide.pdf), [paper](https://arxiv.org/pdf/1706.03374).
- **AugSplicing**: Python 3.6 scripts for streaming tuples, input `(user, object, time(day), edges)`, BSD-3-Clause — [repository](https://github.com/BGT-M/AugSplicing).
- **FRAUDAR**: 2-mode; `rgmining-fraudar` wrapper GPLv3, Python ≥ 3.11, version 0.7.6 (2025-10-22) — [PyPI record](https://pypi.org/pypi/rgmining-fraudar/json); original `camo.zip` — [project page](https://bhooi.github.io/projects/fraudar/index.html).
- **spartan2**: Python, sparse-tensor abstraction, lists HoloScope, Eigenspokes, EagleMine, Fraudar, EigenPulse, FlowScope, CubeFlow, MonLAD, SpecGreedy; D-Cube and AugSplicing do not appear; repository states BSD-3-Clause — [repository](https://github.com/BGT-M/spartan2); PyPI v0.1.3.post4 (2021-12-20) is classified MIT, a discrepancy — [PyPI record](https://pypi.org/pypi/spartan2/json); repository activity continues to 2026-03-30 — [commit feed](https://github.com/stair-team/spartan2/commits/master.atom).
- **SpecGreedy**: 2-mode graphs, Python 3.6, MIT — [repository](https://github.com/wenchieh/specgreedy).
- **StarScout CopyCatch**: runs locally with DuckDB over GH Archive Parquet, Python 3.12+, "16+ GB recommended" RAM, default `DUCKDB_MEMORY_LIMIT` 16 GB and 4 threads, 200–500 GB temp space for large queries, full history "may take days"; last commit 2026-01-25 — [local README](https://github.com/hehao98/StarScout/tree/main/scripts/local), [commit feed](https://github.com/hehao98/StarScout/commits.atom). Apache-2.0 — [repository](https://github.com/hehao98/StarScout). Operates on the star bipartite graph only — [paper](https://arxiv.org/pdf/2412.13459).
- **Not usable as-is**: Spade code is available only on request under NDA — [repository](https://github.com/samjjx/Spade); no public code URL found for ISG+D-Spot — [paper](https://arxiv.org/pdf/1810.06230) — or Dupin — [paper](https://arxiv.org/pdf/2504.09311). CrossSpot's public code had its only commit in 2015 — [commit feed](https://github.com/mjiang89/CrossSpot/commits.atom).

### Inferences
- Scale check: the project's 272k–6.5M tuples are 1–3 orders of magnitude below what M-Zoom/D-Cube were benchmarked on. The closest benchmark is AirForce (648K tuples, 7 modes): 15.6–27.7 s. Assuming near-linear scaling, an hourly tensor should take seconds to about a minute, and a day-long tensor minutes, on a modern CPU (extrapolation; not measured).
- 31 GB RAM is ample for 4-mode runs at this scale: D-Cube's bound is O(Σ|R_n|) memory, and M-Zoom holds tuples in memory, which for 6.5M 4-mode tuples is on the order of hundreds of MB (estimate).
- None of the surveyed dense-block implementations mention GPU execution in the documents I opened, so the RTX 5090 is unlikely to help this stage. Multi-core benefit is limited for the serial Java tools; D-Spot and Dupin are parallel but have no public code.
- Practical recipe: export hourly or daily tuples as integer-coded CSV from DuckDB, call M-Zoom via `subprocess`, parse `block_n.attributes` — straightforward, but GPL-3.0 restricts redistribution of derived code.
- Modelling warning: StarScout's successful lockstep setting uses Δt = 30 days and 6-month chunks; a tensor built on hourly dumps with minute resolution captures only bursts inside the file boundary, which is a different (and narrower) phenomenon. Multi-hour or daily tensors should be tested, with minute resolution compared against coarser bins.

### Gaps
- Actual runtime of these tools on GH Archive 4-mode tensors is untested; the estimates above are extrapolations from the papers' datasets.
- Whether `run_single.sh` in D-Cube works without a Hadoop installation (despite the guide's prerequisite) needs a practical test.

## Q3. What methods exist for coordinated-behaviour detection in social networks, and which handle several action types at once?

### Takeaway
The dominant recipe is a similarity network built from co-actions, thresholded, then clustered, on a single action type per analysis. Multi-action analysis exists (Luceri 2024; Magelinski 2021; Weber & Neumann 2021; Mannocci 2026) but a 2026 survey calls it "a largely unexplored area." These methods use similarity networks or multiplex networks, not dense-block tensor mining, and the survey does not cover dense-block methods at all.

### Cited Findings
- **Pacheco et al.**, "Uncovering Coordinated Networks on Social Media: Methods and Case Studies," ICWSM 2021: unsupervised pipeline, five case studies each on one trace (handle sharing, images, hashtag sequences, co-retweets, synchronization); notes coordination does not imply automation — [arXiv PDF](https://arxiv.org/pdf/2001.05658); Python code covering four case studies, no licence shown — [repository](https://github.com/IUNetSci/coordination-detection).
- **CooRnet** (Giglietto, Righetti, Rossi, Marino, "It takes a village to manipulate the media," Information, Communication & Society, 2020, DOI 10.1080/1369118X.2020.1739732): coordinated link-sharing via CrowdTangle — [ITU listing](https://researcher.itu.dk/en/publications/it-takes-a-village-to-manipulate-the-media-coordinated-link-shari/); repository archived 2 September 2024 because CrowdTangle shut down — [repository](https://github.com/fabiogiglietto/CooRnet). Successor **CooRTweet** v2.2.0 (MIT + file LICENSE, published 2026-11-08) — [CRAN](https://cran.r-project.org/web/packages/CooRTweet/index.html), citation Righetti & Balluff 2025, Computational Communication Research 7(1), works on "any other social media" with appropriately formatted data, no explicit multi-modal support described — [README](https://cran.r-project.org/web/packages/CooRTweet/readme/README.html). **coordination-network-toolkit** (MIT, Python ≥ 3.6): co-retweet, co-tweet, co-similarity, co-link, co-reply, co-post, default 60-second window — [repository](https://github.com/QUT-Digital-Observatory/coordination-network-toolkit).
- **Multi-action methods.** Magelinski, Ng and Carley: synchronized actions on hashtags, URLs and mentions, plus three "higher-order" action types of order two, with multi-view clustering — [arXiv PDF](https://arxiv.org/pdf/2105.07454). Luceri et al. (accepted at the 2024 ACM Web Conference, [arXiv record](https://arxiv.org/abs/2310.09884)): five traces (fast retweet, co-retweet, co-URL, hashtag sequence, text similarity) fused into one network — [PDF](https://arxiv.org/pdf/2310.09884). Weber & Neumann: highly coordinating communities (HCCs) in temporal windows γ ∈ {15, 60, 360, 1440} minutes, with an activity multi-network of hashtag, URL, mention, repost, quote, reply and in-conversation edges — [PDF](https://arxiv.org/pdf/2103.03409). Mannocci et al., Information Sciences 2026 (DOI 10.1016/j.ins.2026.123125): a 5-layer multiplex (co-retweet, co-reply, co-mention, co-hashtag, co-URL), finding that flattening can substantially lose structural information — [PDF](https://arxiv.org/pdf/2507.12108).
- **Survey**: Mannocci, Mazza, Monreale, Tesconi, Cresci, ACM Computing Surveys 58(16), Article 401 (2026) — [arXiv record](https://arxiv.org/abs/2408.01257). It states that "only a few studies" use multilayer analyses, "making the analysis of coordinated behavior across multiple actions a largely unexplored area of research," and describes compound co-actions as almost completely unexplored — [PDF](https://arxiv.org/pdf/2408.01257).
- **Full-text regex check of that survey** (case-insensitive) for `github`, `stack.?overflow`, `software (development|engineering)`, `open.?source`, `copycatch`, `dense.?subgraph`, `dense block`, `tensor`, `positive.?unlabel`, and `leak` returned zero matches (counted on PDF-extracted text) — [PDF](https://arxiv.org/pdf/2408.01257).
- **Other streams**: AMDN-HAGE (Sharma, Zhang, Ferrara, Liu; temporal point processes plus Gaussian mixture, using only account IDs and activity timestamps) — [PDF](https://arxiv.org/pdf/2008.11308). Statistical detectability work (Iannucci, Matakos, Kivelä, October 2026): hypothesis tests on account pairs across 7 coordination modalities and 26 labelled IO datasets, finding common methods can flag groups even when accounts act independently and that dense co-activity alone does not indicate detectability — [arXiv record](https://arxiv.org/abs/2610.37970).

### Inferences
- Cross-event-type analysis on GitHub is conceptually the same move as multi-action coordination on Twitter; the project should cite this literature (Luceri, Magelinski, Weber & Neumann, Mannocci) as direct antecedents rather than claim the idea of cross-action coordination as new.
- The dense-block community and the coordination community barely cite each other, per the survey's zero matches for dense-subgraph terms, so a bridge study is feasible, but connecting two existing lines is a modest contribution.

### Gaps
- Bibliographic details of Nizzoli et al. (ICWSM 2021) and Cinelli et al. (Decision Support Systems 160, 2022) were confirmed only from arXiv records, and their methods were not read in depth. Tardelli et al. (arXiv 2301.06774) was opened only at its front matter.
- Published venue of Sharma et al.: the opened PDF carries a template placeholder ("Woodstock '18"), so the venue is not confirmed here.

## Q4. Has dense-block or coordination mining been applied to GitHub or other software development platforms?

### Takeaway
Yes for stars: StarScout applies CopyCatch to the entire GitHub star graph from GH Archive. It is star-only in its lockstep detector and validates partly via later deletion. Beyond stars I found manual analyses (Stargazers Ghost Network), a Stack Overflow voting-ring study, and a 2026 multi-category abuse framework that reuses StarScout, but cross-event-type dense-block or coordination mining on GitHub was not found in the searches listed.

### Cited Findings
- **StarScout** — He, Yang, Burckhardt, Kapravelos, Vasilescu, Kästner. "Six Million (Suspected) Fake Stars on GitHub: A Growing Spiral of Popularity Contests, Spam, and Malware," ICSE 2026, DOI 10.1145/3744916.3764531; arXiv v1 title was "4.5 Million (Suspected) Fake Stars" — [arXiv record](https://arxiv.org/abs/2412.13459), [PDF](https://arxiv.org/pdf/2412.13459).
  - **Data**: GH Archive, more than 20 TB, stargazer bipartite graph of 326 million edges (July 2019–December 2024), processed in interleaving 6-month chunks on Google BigQuery — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Action types**: the lockstep detector uses only the star graph. A separate "low activity signature" flags accounts with only one WatchEvent plus at most one additional event (e.g., ForkEvent) in the same repository on the same day — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Window and parameters**: CopyCatch with n = 50 accounts, m = 10 repositories, Δt = 30 days, ρ = 0.5, seeded on repositories; post-processing keeps repositories with a month of more than 50 fake stars where fake share exceeds 50%, and an all-time fake share over 10% — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Results**: 6.0 million suspected fake stars across 26,254 repositories (1.06M low-activity, 4.93M lockstep) before post-processing; 18,617 repositories and 301K accounts after (3.81M stars) — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Recall against a known campaign**: Stargazer Ghost Network (847 repositories with more than 50 stars from 15,672 accounts): 688 repositories (81.23%), 11,903 accounts (75.95%). The paper also writes "up to 82.23%" recall for repositories, which is inconsistent with its own count — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Criterion validity via later deletion** (directly relevant to a disappearance target): Table 1, % deleted without/with post-processing. Repositories: baseline 5.03%; Low Activity 14.38%/79.36%; Lockstep 82.03%/90.70%; All 70.05%/90.42%. Accounts: baseline 3.54%; Low Activity 19.19%/72.29%; Lockstep 23.03%/48.83%; All 18.77%/57.07% — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Limits stated by the authors**: ad-hoc thresholds without thorough sensitivity tests, possible false positives (they estimate ~180 false-positive repositories if 99% precise), and evidence insufficient for disciplinary action — [PDF](https://arxiv.org/pdf/2412.13459).
  - **Availability**: Apache-2.0 — [repository](https://github.com/hehao98/StarScout); a local DuckDB path added later — [local README](https://github.com/hehao98/StarScout/tree/main/scripts/local).
- **Stargazers Ghost Network** (Check Point Research, 24 July 2024): more than 3,000 accounts with distinct roles (repository, commit, release, stargazer, forks) that together maintain phishing repositories; more than 380 accounts starred roughly 30 repositories in one campaign; mapped via star anomalies, naming patterns, commit history, emails, timezones and fork relations, largely by hand — [Check Point Research](https://research.checkpoint.com/2024/stargazers-ghost-network/).
- **Abuse taxonomy and detection framework**: Cheng, Zhang, Yu, Ma, Shen, Liu, "Weaponizing the Commons" (JAWs@ICSE 2026): 392 manually labelled instances across abuse categories, F1 above 89%; fake stars are delegated to StarScout and issue spam to an MLP with TF-IDF; a text search of the paper for "coordinat" and "event type" found no matches — [PDF](https://arxiv.org/pdf/2604.17909).
- **Stack Overflow**: Mazloomzadeh, Uddin, Khomh, Sami, "Reputation Gaming in Stack Overflow," studied voting rings using a community-isolation algorithm and a reputation-jump algorithm; 60–80% of flagged users later had reputation reduced — [arXiv record](https://arxiv.org/abs/2111.07101); published as an ICSE 2025 journal-first paper titled "Reputation Gaming in Crowd Technical Knowledge Sharing" — [ICSE 2025 page](https://conf.researchr.org/details/icse-2025/icse-2025-journal-first-papers/36/Reputation-Gaming-in-Crowd-Technical-Knowledge-Sharing).
- **Dense-block evaluation data from a software Q&A site**: M-Zoom used Stack Overflow favourites as one of eight benchmark tensors, but did not study platform abuse there — [PDF](https://www.cs.cmu.edu/~kijungs/papers/mzoomPKDD2016.pdf).

### Inferences
- The strongest precedent for the project's data and pipeline is StarScout. Its deletion criterion shows that lockstep membership correlates with later disappearance (accounts 48.83% lockstep vs 3.54% baseline), which directly supports using disappearance as a noisy positive-like outcome, and means this association cannot be presented as a new discovery.
- Check Point's account-role analysis is evidence that cross-event-type coordination exists on GitHub, which helps motivate the idea but also shows it was already recognised.

### Gaps

## Q5. Have outputs of dense-block or coordination mining been used as features or as labels in downstream classifiers, and did they improve results over behavioural features?

### Takeaway
Yes as features: Vargas et al. (2020), Luceri et al. (2024) and Weber & Neumann (2021) all feed coordination-derived structure into classifiers, and Weber & Neumann already use a bagging PU classifier on combined account and community features. Using dense-block outputs as training labels was not found in the searches listed. Direct head-to-head evidence that coordination features beat behavioural features is scarce; the closest fraud example finds the attribute features dominate.

### Cited Findings
- **Vargas, Emami, Traynor** (arXiv 2005.13466, CCSW 2020 per listing): random forest (100 trees) on statistical features of daily coordination networks for 10 state-attributed campaigns (over 160M tweets). F1 = 0.98 for future activity of known campaigns, F1 = 0.71 for out-of-distribution (cross-campaign) activity, mainly due to false positives; coordination features alone were judged useful as evidence but not ready for deployment at scale — [PDF](https://arxiv.org/pdf/2005.13466).
- **Luceri et al. 2024**: Node2Vec embeddings (128 dimensions) of the fused 5-trace similarity network, random forest with 10-fold cross-validation. Task 1 (per IO): AUC 0.94, F1 0.82, precision 0.96 on average; Task 2 (global): precision 0.95, recall 0.70, F1 0.78, AUC 0.92; abstract also reports AUC 0.95 and F1 0.83. Fused network outperforms each individual trace; ablation shows every trace contributes positively — [PDF](https://arxiv.org/pdf/2310.09884). No comparison to individual account-behaviour features appears in the sections I read.
- **Weber & Neumann** (arXiv 2103.03409; related DOI 10.1007/s13278-021-00815-2 listed on [arXiv record](https://arxiv.org/abs/2103.03409)): explicitly one-class / PU framing ("positive examples... everything else is regarded as unknown"), with features from individual accounts and from their HCC, noting "Feature vectors for members of the same HCC will naturally share the feature values drawn from their grouping." Classifiers: SVM, RF, and a bagging PU classifier (BPU, Mordelet and Vert) with internal 1,000-tree RF; positives from ground-truth coordinating accounts, unlabeled from a RANDOM dataset. BPU accuracy (DS1, γ = 15/60/360/1440): 0.69/0.65/0.60/0.88; (DS2): 0.93/0.92/0.95/0.54. Best-classifier accuracy per dataset-window pair ranged 0.60–0.97 — [PDF](https://arxiv.org/pdf/2103.03409).
- **AMDN-HAGE** (Sharma et al.): learned account embeddings used directly (unsupervised AMDN-HAGE AP 0.804, AUC 0.898) and with supervision (AMDN-HAGE + NN AP 0.838, AUC 0.926) on the IRA dataset; baselines include Co-activity AUC 0.592 and supervised HP(S) AUC 0.925 — [PDF](https://arxiv.org/pdf/2008.11308). The authors decline to use Twitter suspensions as labels: "accounts that are suspended can be due to various reasons... Thus we cannot use Twitter suspensions to estimate precision-recall on coordination detection" — [PDF](https://arxiv.org/pdf/2008.11308).
- **GSRank** (Mukherjee, Liu, Glance, WWW 2012): frequent-itemset mining finds candidate reviewer groups; group and member spam indicators feed a relation-based ranking model; GSRank beat SVMRank, RankBoost and SVR variants, and all improvements at k = 20, 40, 60, 80 were significant at 95% by paired t-tests (exact curves in figures) — [PDF](https://www2.cs.uh.edu/%7Earjun/papers/WWW-2012-group-spam-camera-final.pdf).
- **Cluster-level supervision**: Xiao, Freeman, Hwa, "Detecting Clusters of Fake Accounts in Online Social Networks" (2015; the opened listing shows CCS 2015) classifies whole clusters with supervised statistics of user-generated fields — [truncated abstract](https://www.sciweavers.org/node/359784) (AUC figures and the LinkedIn deployment context not verified; see Unverified).
- **Graph features vs tabular**: Khaleghpour & McKinney (arXiv 2603.06632, 2026) on Elliptic: Random Forest with strict temporal split reaches ROC-AUC ≈ 0.85 and AP ≈ 0.54, and "transaction attributes remain the dominant predictive signal," with graph features complementary — [PDF](https://arxiv.org/pdf/2603.06632).
- **Labels**: TwiBot-22 uses weak supervision (Snorkel, 8 labeling functions and 7 models, plus 1,000 expert annotations), but nothing based on dense-block outputs — [PDF](https://arxiv.org/pdf/2206.04564). StarScout's output is "suspected" fake activity and its authors caution about false positives — [PDF](https://arxiv.org/pdf/2412.13459).

### Inferences
- The claim that "mined coordination structure as classifier input" is new is defeated by Vargas 2020, Luceri 2024 and Weber & Neumann 2021. The PU part is also not new given Weber & Neumann's BPU on account plus community features.
- Weber & Neumann's sentence on shared group feature values is exactly the leakage mechanism C2's grouped splits target, and the paper evaluates with two-fold validation without a stated group split, so C2's grouped-split element is a legitimate improvement in rigour, but not a new idea (see Q7).
- The project must include an ablation (behavioural-only vs behavioural + dense-block) because the literature found does not establish incremental value over behavioural features; the Elliptic result suggests the increment may be modest.

### Gaps
- Not found in the searches listed: dense-block outputs (FRAUDAR/M-Zoom/D-Cube/CopyCatch membership or score) used as features or labels in a supervised or semi-supervised classifier, with an ablation against behavioural features. Searches: "dense subgraph score as feature supervised fraud classifier FRAUDAR features improves GNN"; "account coordination features improve bot detection classifier ablation "coordination" feature importance over behavioral features"; arXiv `abs:FRAUDAR AND abs:feature` (no results); "positive-unlabeled learning coordinated inauthentic accounts information operations group features classifier".
- ANTICO (KDD 2022) formulates cash-out detection as dense-block mining but is detection rather than downstream use, and only its abstract was read; a 2023 Neurocomputing paper on dense-subgraph reconstruction before a GNN was seen only in a search snippet (see Unverified).

## Q6. How are dense-block detectors evaluated, and what are the known weaknesses of these evaluations?

### Takeaway
Three styles dominate: injected synthetic blocks scored with F-measure or FAUC, labelled intrusion data scored with AUC, and small manual audits or proxy outcomes on real platforms. Each has a known weakness: injection matches the detector's assumed shape, the intrusion data have documented flaws, and proxy outcomes such as deletion or suspension are not coordination ground truth.

### Cited Findings
- **Injection**: FRAUDAR injects dense blocks into an Amazon subgraph and reports F-measure — [PDF](https://bhooi.github.io/papers/fraudar_kdd16.pdf); EigenPulse measures lowest detection density and speed at F-measure 90% — [PDF](https://shenghua-liu.github.io/assets/pdf/papers/pakdd2019-eigenpulse.pdf); CubeFlow uses FAUC under varying injection ratios — [PDF](https://arxiv.org/pdf/2103.12411); DenseAlert counts a miss if the injected subtensor is not in the top 10 densest or is hidden in a subtensor 10x larger — [PDF](https://arxiv.org/pdf/1706.03374); ISG injects hidden-densest blocks with parameter λ — [PDF](https://arxiv.org/pdf/1810.06230).
- **Labelled intrusion data and AUC**: M-Zoom AUC 0.98 on AirForce TCP — [PDF](https://www.cs.cmu.edu/~kijungs/papers/mzoomPKDD2016.pdf); D-Cube Table 4 AUCs on AirForce and DARPA — [PDF](https://www.cs.cmu.edu/~kijungs/papers/dcubeWSDM2017.pdf); DenseAlert AUC 0.924 on a TCP dump — [PDF](https://arxiv.org/pdf/1706.03374).
- **Manual audit and known lists**: CopyCatch's 22 labelled clusters (100% deceitful) — [paper via Meta page](https://ai.meta.com/research/publications/copycatch-stopping-group-attacks-by-spotting-lockstep-behavior-in-social-networks/); FRAUDAR's hand-checked Twitter block — [PDF](https://bhooi.github.io/papers/fraudar_kdd16.pdf); StarScout's recall against the Stargazer Ghost Network and deletion-based criterion validity — [PDF](https://arxiv.org/pdf/2412.13459); Luceri and Mannocci use Twitter's information-operation labels as proxies — [Luceri](https://arxiv.org/pdf/2310.09884), [Mannocci](https://arxiv.org/pdf/2507.12108).
- **Weakness — injected or synthetic structure**: BOND reports that organic outliers need not fit injected definitions and that most deep graph outlier detectors perform suboptimally on organic outliers; "detecting organic outliers [is] more difficult than detecting synthetic outliers that follow a specific pattern" — [BOND](https://arxiv.org/pdf/2206.10071).
- **Weakness — intrusion benchmarks**: Tavallaee et al. found about 78% and 75% of KDD train and test records duplicated, and note the dataset still suffers from problems raised by McHugh — [CISDA 2009](https://www.ee.torontomu.ca/~bagheri/papers/cisda.pdf).
- **Weakness — no ground truth**: the coordination survey states that a posteriori characterisation "lacks objective ground truth and limits reproducibility and comparability across methods" — [PDF](https://arxiv.org/pdf/2408.01257); Luceri et al. attribute high similarity thresholds partly to "the absence of ground truth in previous studies" — [PDF](https://arxiv.org/pdf/2310.09884); Mannocci et al. stress that IO-versus-control labels are "an approximation" — [PDF](https://arxiv.org/pdf/2507.12108).
- **Weakness — proxy outcomes**: AMDN-HAGE refuses suspensions as labels (quote in Q5) — [PDF](https://arxiv.org/pdf/2008.11308); StarScout itself uses deletion as a validity signal while cautioning that detected accounts may be false positives and that thresholds were not fully sensitivity-tested — [PDF](https://arxiv.org/pdf/2412.13459).
- **Weakness — over-detection**: Iannucci et al. (2026) show common methods can flag groups even when accounts act independently, and that dense co-activity alone does not indicate whether an operation can be detected — [arXiv record](https://arxiv.org/abs/2610.37970).
- **Weakness — collection artefacts**: Hays et al. show shallow decision trees reach near state-of-the-art on bot benchmarks and that performance collapses across datasets, which they attribute to collection and labelling rather than bot differences — [PDF](https://arxiv.org/pdf/2301.07015).

### Inferences
- Injected-block results are poor evidence for GitHub: real coordinated accounts rarely match a clean block, particularly across event types. Validation on the project's data should use time-held-out disappearance labels and an external coordinated list (Stargazer Ghost Network accounts, if available via StarScout's dataset), not injection alone.
- Given AMDN-HAGE's caution, "disappeared accounts" must be presented as a noisy proxy that mixes spam removals, self-deletion and account renames, not as coordination ground truth.

### Gaps
- A published critique specific to injection in dense-block detection (as opposed to attributed-graph outlier detection) was not found in the searches listed ("injected anomalies graph anomaly detection benchmark bias injection unrealistic BOND outlier detection findings").
- McHugh (2000) was not opened; its content is cited only through Tavallaee et al.'s reference to it.

## Q7. Is splitting data by connected component or coordination cluster standard practice in fraud, bot or graph-based detection? What leakage does it prevent and how large is it?

### Takeaway
Group-aware hold-out is an established principle (Roberts 2017; GroupKFold) and is common in bot-detection benchmarks (LOBO 2018; TwiBot-22 community folds), but coordination and fraud papers often still use random or transductive splits. The project cannot claim grouped splits as new; it can only claim to apply them carefully and, ideally, to measure their effect. Measured leakage for coordination-cluster splits specifically was not found in the searches listed; the nearest measured effects are large.

### Cited Findings
- **General principle**: Roberts et al., Ecography 40:913–929 (2017), state that ignoring temporal, spatial, hierarchical or phylogenetic structure in cross-validation "result[s] in serious underestimation of predictive error" and recommend blocked CV — [PDF](https://www.biometrie.uni-freiburg.de/mitarbeiter/dormann/roberts-et-al-2017-ecography.pdf). scikit-learn's `GroupKFold` is a "K-fold iterator variant with non-overlapping groups" — [documentation](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupKFold.html). Kapoor & Narayanan document leakage across 17 fields and 329 papers, including train and test samples from the same people or units — [arXiv record](https://arxiv.org/abs/2207.07048), [PDF](https://arxiv.org/pdf/2207.07048).
- **Security ML**: Arp et al. (USENIX Security 2022) report data snooping present in 57% of 30 reviewed top-tier papers — [PDF](https://arxiv.org/pdf/2010.09470). TESSERACT shows that k-fold CV "is likely to include in the training set at least one sample of each malware family"; F1 falls from 0.91 (10-fold CV, ALG1, 10% malware in train and test) to 0.58 under temporally consistent evaluation, and from 0.83 to 0.32 for ALG2 — [PDF](https://arxiv.org/pdf/1807.07838).
- **Bot detection**: LOBO (Echeverría et al., ACSAC 2018) holds out whole bot classes. A classifier reaching over 97% accuracy has average accuracy of 54.88% on unseen bot classes, and some held-out botnets fall below 1% detection — [PDF](https://arxiv.org/pdf/1809.09684). TwiBot-22 (NeurIPS 2022 Datasets and Benchmarks) uses 10 sub-communities as folds, training on fold i and testing on fold j — [PDF](https://arxiv.org/pdf/2206.04564). Hays et al. (WWW 2023) leave-one-dataset-out: for example twibot-2020 drops from in-sample accuracy/F1/balanced accuracy 0.80/0.84/0.78 to out-of-sample 0.52/0.44/0.55, and yang-2013 from 0.84/0.88/0.83 to 0.32/0.21/0.62, while midterm-2018 barely changes (0.78/0.82/0.77 vs 0.77/0.85/0.77) — [PDF](https://arxiv.org/pdf/2301.07015).
- **Influence operations**: Vargas et al. report F1 0.98 for same-campaign prediction vs 0.71 cross-campaign, which is the closest measured analogue to a coordination-network hold-out — [PDF](https://arxiv.org/pdf/2005.13466). Gabriel, Broniatowski, Johnson (arXiv 2305.16544) train and test across operations from different countries using inductive graph learning — [arXiv record](https://arxiv.org/abs/2305.16544).
- **Practice is inconsistent**: Luceri et al. use 10-fold cross-validation with embeddings of a single fused network — [PDF](https://arxiv.org/pdf/2310.09884). Weber & Neumann use two-fold validation while noting shared group features — [PDF](https://arxiv.org/pdf/2103.03409). A 2026 fraud preprint (Sharma, "Toward Auditable Fraud Detection") explicitly computes node2vec features on the full graph before a random split and states that "Individual transactions, rather than entire rings, are randomly assigned... Transactions from the same ring may therefore appear in both training and test data" — [PDF](https://arxiv.org/pdf/2607.19266). Khaleghpour & McKinney (2026) warn that graph features computed on the full graph can leak future edges and enforce time-respecting computation — [PDF](https://arxiv.org/pdf/2603.06632). Refnd (arXiv 2607.19376, 2026) reports lower but "more realistic" performance under relational-structure-aware splits in biochemical data — [arXiv record](https://arxiv.org/abs/2607.19376).

### Inferences
- Do not present cluster-grouped splitting as a novelty. Frame it as following LOBO/GroupKFold/TwiBot-22 practice, and consider measuring random-split vs block-grouped-split performance as a concrete empirical contribution (the Vargas gap of 0.27 F1 and LOBO gap of roughly 42 points are the kind of numbers worth replicating for GitHub).
- A second, separate leakage issue will be the larger one: dense blocks mined on the whole time span use future co-activity. Features must be computed only on events before each prediction cutoff, and blocks must be re-mined per training window, otherwise a grouped split still leaks through future edges.

### Gaps
- Not found in the searches listed: any paper measuring performance inflation specifically from splitting by connected component or dense-block cluster versus random splitting in coordinated-account or fraud-ring detection. Searches: "leave-one-botnet-out group split leakage bot detection connected component train test"; "connected component split graph fraud detection data leakage train test GNN inductive group cross-validation entity"; "TwiBot-22 unseen community split bot detection generalization benchmark community-based train test". arXiv query `abs:"coordinated" AND abs:"leakage" AND abs:"split"` failed with HTTP 429.

## Q8. The five closest prior works to C2, with concrete differences, and an explicit verdict

### Takeaway
C2 as a method is not novel. Each ingredient has direct precedent: N-way dense blocks with a categorical mode (Shin et al.), lockstep mining on GH Archive (StarScout), coordination features in classifiers including PU (Weber & Neumann), multi-action fusion (Luceri), and group-aware evaluation (LOBO, TwiBot-22). What I did not find, in the searches listed, is this specific combination applied to GitHub account disappearance. That is an applied and empirical contribution at best, and it risks being judged a straightforward combination of known parts.

### Cited Findings

**Five closest prior works**

1. **Weber & Neumann (arXiv 2103.03409; submitted to SNAM; related DOI 10.1007/s13278-021-00815-2)** — temporal-window coordination mining over multiple interaction types, account plus community features, bagging PU classifier against an unlabeled set — [PDF](https://arxiv.org/pdf/2103.03409), [arXiv record](https://arxiv.org/abs/2103.03409). **Differences from C2**: Twitter not GitHub; communities from an inferred account network, not dense-block tensors; positives are labelled coordinating accounts, not later disappearance; two-fold validation with no stated group split.
2. **Luceri, Pantè, Burghardt, Ferrara (accepted at the 2024 ACM Web Conference, arXiv 2310.09884)** — five-trace fused similarity network, Node2Vec embeddings into a random forest (AUC 0.94 and 0.92) — [PDF](https://arxiv.org/pdf/2310.09884), [arXiv record](https://arxiv.org/abs/2310.09884). **Differences**: Twitter; similarity networks, not tensors; fully supervised rather than PU; 10-fold CV without a stated grouping.
3. **Vargas, Emami, Traynor (arXiv 2005.13466)** — coordination-network statistical features in a binary classifier; measured cross-campaign drop F1 0.98 to 0.71 — [PDF](https://arxiv.org/pdf/2005.13466). **Differences**: classifies daily network activity rather than accounts; Twitter; supervised; no dense blocks; no event-type tensor.
4. **He et al., StarScout (ICSE 2026)** — CopyCatch on all GitHub stars from GH Archive, with deletion as criterion validity — [PDF](https://arxiv.org/pdf/2412.13459). **Differences**: star graph only (fork appears only as an allowance in the low-activity heuristic); 30-day windows; repository campaign detection; no downstream classifier, no PU, no grouped split.
5. **Shin et al. dense-subtensor family (M-Zoom, D-Cube, DenseAlert) and ISG+D-Spot** — N-way dense blocks, including 4-way tensors with a categorical mode (users, items, timestamps, ratings) — [DenseAlert](https://arxiv.org/pdf/1706.03374), [M-Zoom](https://www.cs.cmu.edu/~kijungs/papers/mzoomPKDD2016.pdf); ISG for blocks dense on only some modes — [ISG](https://arxiv.org/pdf/1810.06230). **Differences**: event type is not used as a mode (rating value and other attributes are); no GitHub; outputs are used for detection, not as classifier inputs; no PU.

**Runners-up**: Mannocci et al. 2026 (5-layer multiplex multimodal coordination) — [PDF](https://arxiv.org/pdf/2507.12108); Magelinski et al. (multi-view synchronized actions) — [PDF](https://arxiv.org/pdf/2105.07454); GSRank 2012 (mined groups fed to a ranking model) — [PDF](https://www2.cs.uh.edu/%7Earjun/papers/WWW-2012-group-spam-camera-final.pdf); LOBO 2018 and TwiBot-22 for group-aware evaluation — [LOBO](https://arxiv.org/pdf/1809.09684), [TwiBot-22](https://arxiv.org/pdf/2206.04564).

### Inferences
- Decomposition of C2 into claims:
  - "Dense-block mining on a multi-attribute tensor with a categorical mode": **already standard** (M-Zoom/D-Cube; event type replaces rating or attribute modes).
  - "Cross-event-type on GitHub": **not found in the searches listed**; this is the most defensible specific element.
  - "Coordination structure as classifier features": **already done** (Vargas 2020; Luceri 2024; Weber & Neumann 2021).
  - "PU classification on coordination features": **already done** in one prior study (Weber & Neumann 2021), though with a different label and platform.
  - "Disappearance as outcome linked to lockstep": **association already shown** (StarScout's deletion criterion); use as a downstream prediction target on GitHub was not found in the searches listed.
  - "Cluster-grouped splits": **not new as a principle** (LOBO, TwiBot-22, GroupKFold); inconsistently applied in practice.
- Recommended honest framing for the project: an empirical study, not a method: "We test whether cross-event-type dense-block features add predictive value over account-level behavioural features for PU prediction of GitHub account disappearance, and we quantify how much of the apparent performance comes from coordinated-network leakage (random vs block-grouped splits, with features computed strictly before the prediction cutoff)." The ablation and the leakage measurement are the parts that would be new to report.
- Risk statement: if the only result is "we applied M-Zoom plus a PU classifier to GH Archive and used GroupKFold," reviewers would be right to call it a straightforward combination.
